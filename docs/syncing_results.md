# Syncing data to the server

> **Two different tools live in this repo. Pick the right one.**
>
> | | `server_sync/sync_server.sh` | `deploy/sync-results.sh` |
> |---|---|---|
> | trees | `notes/` + `Results/` (rsync) **and** `recommendations/` (Unison, two-way) | `Results/` only |
> | run | **by hand**, from the workstation project dir | unattended, systemd timer |
> | use when | you are the admin, and `recommendations/` must come *back* from the server | a sender machine only ever pushes `Results/` |
>
> **The admin workflow is `server_sync/sync_server.sh`** — it is the only one
> that brings reviewer submissions back. See
> [its README](../server_sync/README.md), and the
> [by-hand multi-project section](#by-hand-admin-sync-server_syncsync_serversh)
> below. The rest of this file documents `deploy/sync-results.sh`, the
> push-only timer-driven tool.

---

## Part 1 — `deploy/sync-results.sh`: pushing `Results/` only

How clustering output gets from the machine that produces it (the **sender**)
to the machine that serves the review app (the **host**), one project at a
time, without destroying anything.

Read the two rules first. Everything else is mechanics.

---

## The two rules

### 1. `TARGET_DIR` is the project's `Results/` directory. Never its parent.

```
right:  .../data/MOJAVE/Results
WRONG:  .../data/MOJAVE
```

The sync mirrors with `rsync --delete`, so anything in `TARGET_DIR` that is
not in `SOURCE_DIR` is **removed**. Point it one level short and rsync deletes
`recommendations/` and `notes/` — the only irreplaceable data on the server.
`Results/` can be regenerated by the pipeline; reviewer recommendations cannot.

`MAX_DELETE` does **not** protect you here. That mistake removes a handful of
entries (`recommendations/`, `notes/`, `Results/`, two CSVs), far under the
default cap of 1000. Verified by dry-run:

```
*deleting recommendations/0003-066u/mll.json
*deleting recommendations/
*deleting notes/
```

`sync-results.sh` now **refuses** a target containing `recommendations`,
`notes`, `config`, `tokens.yaml`, `fits_cache` or `logs`, so the common slip is
caught before any transfer. That guard is belt-and-braces, not a licence to be
careless — it only recognises directories that already exist.

### 2. One config file per project. The sync is never "all projects at once".

Each project is an independent `SOURCE_DIR` → `TARGET_DIR` pair. There is no
mode that walks several projects, deliberately: a single `--delete` mirror
spanning project roots is the mistake in rule 1 with extra steps.

```
~/.config/mojave-results-sync-mojave.conf
~/.config/mojave-results-sync-bk224.conf
```

## Sender setup (once per machine)

Needs `rsync` and key-based SSH to the host with no password prompt:

```bash
ssh-keygen -t ed25519                 # if you don't have a key
ssh-copy-id homand@mojave.denison.edu
ssh homand@mojave.denison.edu true    # must succeed silently
```

Install the script:

```bash
mkdir -p ~/bin ~/.config
cp deploy/sync-results.sh ~/bin/mojave-review-sync
chmod +x ~/bin/mojave-review-sync
```

The script is self-contained — no Python, no package install. Copying that one
file plus a config is enough on a machine that only ever syncs.

**macOS senders work.** Progress reporting is version-probed: `--info=` arrived
in rsync 3.1, and macOS ships openrsync ("rsync version 2.6.9 compatible")
where passing it aborts with a usage dump before transferring anything. The
script falls back to `--stats --verbose`.

## Per-project setup

```bash
cp deploy/mojave-results-sync.conf.example \
   ~/.config/mojave-results-sync-mojave.conf
```

Edit the four required values:

| key | value |
|---|---|
| `SOURCE_DIR` | this project's `Results/` on the sender |
| `TARGET_USER` | SSH user on the host |
| `TARGET_HOST` | hostname or LAN IP |
| `TARGET_DIR` | this project's `Results/` **on the host** — rule 1 |

`TARGET_DIR` must agree with the project `root` in the host's `config.yaml`:
if `root` is `…/data/MOJAVE`, then `TARGET_DIR` is `…/data/MOJAVE/Results`.

### Dry-run first. Always.

```bash
MOJAVE_SYNC_CONF=~/.config/mojave-results-sync-mojave.conf \
    mojave-review-sync --dry-run
```

Read the `*deleting` lines before the transfer lines. On a routine sync they
should be empty or confined to source folders you know you removed upstream. If
you see `recommendations` or `notes`, stop — that is rule 1, and the guard
should already have refused.

Then for real:

```bash
MOJAVE_SYNC_CONF=~/.config/mojave-results-sync-mojave.conf mojave-review-sync
```

### Schedule it

Templated units, so one unit file serves every project:

```bash
mkdir -p ~/.config/systemd/user
cp deploy/mojave-results-sync@.service ~/.config/systemd/user/
cp deploy/mojave-results-sync@.timer   ~/.config/systemd/user/
systemctl --user daemon-reload

systemctl --user enable --now mojave-results-sync@mojave.timer
systemctl --user enable --now mojave-results-sync@bk224.timer
loginctl enable-linger $USER          # fire while logged out
```

The instance name is the project: `@bk224` reads
`~/.config/mojave-results-sync-bk224.conf`. Adding a project is a config file
plus one `enable` — no unit to copy or edit.

```bash
systemctl --user list-timers 'mojave-results-sync@*'
journalctl --user-unit 'mojave-results-sync@bk224'
```

Single-project deployments can keep the older non-templated
`mojave-results-sync.service` / `.timer` pair, which reads the default
`~/.config/mojave-results-sync.conf`.

## Adding a new project

Order matters: the app skips a project whose data is absent, so syncing first
means it appears the moment you enable it.

1. **Create the project root on the host** and sync its `Results/`:
   ```bash
   ssh homand@HOST 'mkdir -p /…/data/NEWPROJ'
   cp deploy/mojave-results-sync.conf.example \
      ~/.config/mojave-results-sync-newproj.conf   # edit it
   MOJAVE_SYNC_CONF=~/.config/mojave-results-sync-newproj.conf \
       mojave-review-sync --dry-run                # then for real
   ```
2. **Copy the support files** into the project root (not `Results/`, and not a
   shared parent — each project discovers its own from its root):
   ```bash
   scp source_run_param.csv astrometry_mojave.dat homand@HOST:/…/data/NEWPROJ/
   ```
   `astrometry_mojave.dat` is optional; without it the "Astrometric reference"
   option shows `(no astrometry file)` and is disabled, which is correct rather
   than broken.
3. **Add it to `config.yaml`** under `projects:` and restart:
   ```bash
   sudo systemctl restart mojave
   ```
4. **Confirm** in the journal — one `mounted project` line per project, and no
   `project skipped:` lines:
   ```bash
   sudo journalctl -u mojave -n 30 --no-pager | grep -E 'mounted project|skipped'
   ```
5. **Enable its timer** on the sender (above).

`recommendations/` and `notes/` are created by the app as reviewers work;
they are never synced.

## What the sync does and does not touch

| path | synced? |
|---|---|
| `<root>/Results/` | **yes** — mirrored, with `--delete` |
| `<root>/recommendations/` | no — server-owned, the irreplaceable artifact |
| `<root>/notes/` | no — server-owned |
| `<root>/source_run_param.csv`, `astrometry_mojave.dat` | no — copy by hand when they change |
| `data/fits_cache/`, `data/logs/` | no — shared, server-owned |

The direction is strictly one-way, sender → host. Nothing the app writes is
ever sent back, and nothing the sync does can modify the reviewers' work.

The support files sitting outside the sync is a deliberate trade (they change
rarely, and a stale redshift table is a quiet wrong-answer rather than a
crash) — but it does mean **remembering to copy them** when a project's
`source_run_param.csv` is updated. Symptom of a missing one: the Flux view
reads `Tb obs [K]` instead of `Tb host-frame [K]`, and `beta_app` disappears
from the Kinematics hovers.

## Safety rails in the script

| rail | behaviour |
|---|---|
| target guard | refuses a `TARGET_DIR` containing `recommendations`/`notes`/etc. Override: `ALLOW_UNSAFE_TARGET=1` |
| `MAX_DELETE` | default 1000; rsync aborts and changes **nothing** if exceeded. Catches "Drive mirror briefly empty". `MAX_DELETE=0` disables |
| SSH preflight | `BatchMode=yes`, 10 s timeout — fails fast instead of hanging a timer |
| `--partial` | an interrupted transfer resumes rather than restarting |
| excludes | `.DS_Store`, `._*`, `~$*`, `.gdshortcut*`, `*.tmp`, `*.partial` |

`MAX_DELETE` guards against a truncated source. The target guard covers a
mistyped destination. Neither covers pointing `SOURCE_DIR` at the wrong
*project* — that would mirror project A's sources into project B, which both
rails read as a legitimate bulk change. Check the dry-run.

## Troubleshooting

**`REFUSING to sync — the target does not look like a Results/ directory`**
Rule 1. `TARGET_DIR` is one level too high.

**`SSH to …  failed`** Key-based SSH isn't working non-interactively. Test with
`ssh -o BatchMode=yes USER@HOST true`.

**rsync aborts with `--max-delete` exceeded, nothing transferred** The source
lost a lot of content — a half-mounted cloud mirror, or an interrupted
pipeline run. Investigate the source before raising the cap.

**rsync prints a usage dump immediately** A pre-3.1 rsync reached a flag it
doesn't support. The script probes for `--info=`; if you added
`EXTRA_RSYNC_OPTS`, check those.

**A project is missing from the switcher after a restart**
```bash
sudo journalctl -u mojave -n 50 --no-pager | grep -i 'project skipped'
```
Usually "no such directory" (root not created) or "has no Results/" (synced to
the wrong place, or the sync hasn't run).

**The whole site is down after a config change** Startup fails only when *no*
project is usable. Same grep; if every project is skipped, a shared path is
wrong.

## By-hand admin sync (`server_sync/sync_server.sh`)

The tool above pushes `Results/` and nothing else. The admin workflow needs
three legs, because `recommendations/` is written on **both** sides —
reviewers submit on the server, the admin aggregates and applies locally:

| tree | direction | tool | `--delete`? |
|---|---|---|---|
| `notes/` | workstation → server | rsync mirror | yes |
| `Results/` | workstation → server | rsync mirror | yes |
| `recommendations/` | workstation ⇄ server | **Unison** | no |
| `recommendations/_admin/` | workstation → server | rsync mirror | yes |

Full rationale — why Unison rather than two-way rsync, conflict handling, the
backup buffer — is in [`../server_sync/README.md`](../server_sync/README.md).

### Multi-project: the project name is now mandatory

```bash
cd ~/Dropbox/Research/Clustering_CC/MOJAVE_1996.00-2026.00
/path/to/repo/server_sync/sync_server.sh MOJAVE            # preview
/path/to/repo/server_sync/sync_server.sh MOJAVE run        # apply
```

`PROJECT` is the **server-side** directory name under `REMOTE_DATA`
(`MOJAVE`, `BK224`) — not the workstation directory name, which may differ
(`MOJAVE_1996.00-2026.00` → `MOJAVE`). It has no default on purpose: the old
flat layout would otherwise be silently assumed, which both strands the data
in a stale tree and — the dangerous part — points Unison at a root its
archive no longer matches.

The script refuses if the remote project root doesn't exist, rather than
letting rsync create `…/data/<typo>/Results` and report success.

The authority for what `PROJECT` should be is the app's own startup log:

```bash
sudo journalctl -u mojave -n 30 --no-pager | grep 'mounted project'
```

### One Unison profile per project

Unison keys its state archive on the **root pair**. One profile reused across
projects would thrash a single archive between two remote roots, and each
switch would read as "everything was deleted over there". So:

```bash
cp server_sync/mojave-recs-webby-PROJECT.prf ~/.unison/mojave-recs-webby-MOJAVE.prf
cp server_sync/mojave-recs-webby-PROJECT.prf ~/.unison/mojave-recs-webby-BK224.prf
```

Edit the one marked `root = ssh://…` line in each to that project's
`recommendations` directory. The profile name after `mojave-recs-webby-` must
match the `PROJECT` argument — `sync_server.sh` derives it.

### The hazard worth understanding before the first run

Unison's archive remembers the previous state **of a specific root pair**. The
server's `recommendations/` has just moved from `…/data/recommendations` to
`…/data/<PROJECT>/recommendations`. Two outcomes:

- **New root in the profile** (what you want): no archive for the new pair, so
  Unison reconciles from scratch. Safe — it compares contents, so identical
  files produce no action — but it may surface conflicts to decide, and takes
  one slow pass.
- **Old root left in place**: the path no longer exists. Unison either errors
  (safe) or, if something recreated an empty directory there, reads the
  archive and concludes the remote deleted everything — then proposes deleting
  it on the **workstation** too.

So, in order:

1. Install the per-project profiles with the **new** roots.
2. Run `preview` and actually read the Unison plan. Deletions on the
   workstation side are the thing to look for.
3. Only use `run` once the plan looks right.
4. **Do not use `auto` until an interactive run has succeeded.** `auto` passes
   `-batch -auto -prefer newer`, which answers those prompts for you.

Overwritten and deleted files are kept under `/tmp/unison-mojave-backups/`
(last 5 versions) on whichever host the change landed — a short-term undo
buffer, cleared on reboot.

### Support files are not synced by either tool

`source_run_param.csv` and `astrometry_mojave.dat` live in the project root,
outside all four legs. Copy them by hand when they change:

```bash
scp source_run_param.csv astrometry_mojave.dat     homand@HOST:/…/data/MOJAVE/
```

Symptom of a missing redshift table: the Flux view reads `Tb obs [K]` instead
of `Tb host-frame [K]`, and `beta_app` vanishes from the Kinematics hovers.
